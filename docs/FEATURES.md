# Feature Guide: what each part does and how we built it

Every page of the app, explained for a reader who has not seen the code: what you see, what it teaches, and how it
works underneath. File paths are relative to the repository root.

---

## The app shell

**What it does.** A left rail lists the seven tools. Each tool has its own colour (red, orange, brass, violet, teal,
green, blue); the colour follows you into that page's buttons, focus rings and charts. On a phone the rail becomes a
"Tools" menu. A footer credits the course and the team.

**How we built it.**
- `frontend/src/components/Shell.tsx` — React Router layout. The active tool's colour is set as the CSS variable
  `--tool`, so every component can use `var(--tool)` without knowing which page it is on.
- Page changes fade and rise 8 px using Motion's `AnimatePresence` (220 ms, ease-out).
- `frontend/src/lib/store.ts` — a tiny shared store (`useSyncExternalStore`) so the password you type on one page is
  already filled in on the next. It lives only in memory; reloading the page clears it.
- Design tokens (colours, fonts, easing) live in `frontend/src/index.css` under `@theme` (Tailwind CSS 4).

## 1. Analyzer

**What it does.** Type a password and see, live:
- a needle on a 0–128 **bit scale** (how many guesses, as a power of two),
- **two verdicts**: zxcvbn's and our ML model's, with the model's confidence,
- **time to crack** for five attacker profiles, from a throttled login form to an offline GPU,
- **patterns** found (dictionary word, sequence, keyboard walk, repeated characters, dates),
- a **NIST SP 800-63B** checklist.

**How we built it.**
- `lib/strength.ts` wraps **zxcvbn-ts** with its English and common-password dictionaries. zxcvbn returns an
  estimated guess count; bits = log₂(guesses).
- `lib/rates.ts` holds the guess rate for each profile (with its source) and turns `guesses ÷ rate` into readable
  text ("3 hours", "centuries").
- `lib/features.ts` + `lib/data.ts` compute 17 numbers about the password and run them through the trained model
  (see ML Lab).
- `lib/nist.ts` checks length, common-password list, repeats and sequences.
- `components/BitScale.tsx` draws the ruled scale; the needle moves with a spring animation.

## 2. Attack Simulator

**What it does.** Shows visually why short or common passwords are weak, in three modes (brute force, dictionary,
hybrid). The signature visual is a row of "drums", one per character, that spin and lock — inspired by the
Bletchley Park bombe machines. Beside it, a table shows how long a real offline attack would take.

**Important:** this is an animation driven by the password you typed in your own browser. It does not process
hashes, does not contact any server, and cannot be pointed at anyone else's data. The page says so, and also notes
that per-character locking is a visual simplification.

**How we built it.**
- `components/Drum.tsx` — each drum cycles glyphs with `requestAnimationFrame` (every 45 ms) and "clicks" into place
  with a short scale bounce when it locks. With reduced-motion turned on, drums simply show the final character.
- `lib/attack.ts` produces a list of animation frames; the page plays them on a timer.
- The word list used for the list-based modes is **synthetic**, generated by our own script (`ml/build.py`).

## 3. Hashing Lab

**What it does.** Hashes the same password four ways — **MD5, SHA-256, bcrypt, Argon2id** — and shows the digest,
whether it is salted, and how long one hash took. Typical result: MD5 ≈ 0.005 ms, bcrypt ≈ 300 ms, about 66,000×
slower. Each digest is also drawn as a bar pattern made from its bytes; change one character and the whole pattern
changes (the "avalanche effect").

**What it teaches.** Fast hashes are the wrong tool for passwords. Slow, salted, memory-hard hashing (Argon2id) is the
current recommendation.

**How we built it.**
- **hash-wasm** runs all four algorithms in the browser through WebAssembly — so this page works even when our server
  is asleep, and the password is never sent.
- Timing pitfall we fixed: the first call includes WebAssembly start-up, which made MD5 look slow (12 ms). We now
  warm up every algorithm first and time fast hashes over 2,000 repetitions.
- `components/ui.tsx → HashBars` draws the byte-bar pattern.

## 4. Rainbow Table

**What it does.** Explains precomputed tables, the reason unsalted hashes are dangerous. Enter a short lower-case
word: its unsalted MD5 is found in a small table on our server. Add a salt and the same word is **not** found —
which is the whole lesson.

**Scope.** The table only covers 4–5 letter lower-case words (about 12 million strings) — a deliberately tiny,
educational keyspace.

**How we built it.**
- `backend/build_rainbow.py` builds the table once, offline, using all CPU cores (~3 minutes). The result is a
  150 KB file (`backend/data/rainbow_md5_l45.bin`).
- `backend/app/rainbow.py` loads it and answers lookups; `POST /rainbow/lookup` returns whether it was found, the
  time taken and a short trace that the page animates.
- Measured coverage of the keyspace: ~79%.

## 5. Bulk Audit

**What it does.** Upload a CSV of **synthetic** user hashes (or click "Use sample dataset") and get an audit:
how many accounts use weak storage (MD5/SHA), how many passwords appear in a small common-password list, which
passwords are reused, and written recommendations. One click downloads a PDF report — the kind of summary a security
review hands to a client.

**Safeguards.** Uploads are limited to 400 KB / 500 rows and 20 requests per minute. Only fast, unsalted hashes are
checked; bcrypt and Argon2id entries are reported as properly stored. Recovered passwords are masked (`pa*****d`).
Nothing is saved on the server.

**How we built it.**
- `backend/app/audit.py` parses the CSV, detects each row's algorithm from its format, compares against a
  precomputed table built from our synthetic list, and assembles the statistics.
- `backend/app/report.py` renders the same result as a PDF with **ReportLab** (pure Python, so it installs on free
  hosting).
- `GET /audit/sample` serves the bundled synthetic CSV.

## 6. Generator

**What it does.** Makes strong passwords. Two modes:
- **Random** — choose length (6–40) and character sets; option to drop look-alike characters (I, l, 1, O, 0).
- **Passphrase** — 3–8 words from the EFF wordlist, with separator and capitalisation options.

It shows the **true entropy** (e.g. 100 bits for 16 random characters) and the offline crack time, and "Analyze →"
sends the result to the Analyzer.

**How we built it.**
- Randomness comes from `crypto.getRandomValues` (the browser's cryptographic generator), never `Math.random`.
- Entropy = length × log₂(alphabet size), or words × log₂(7,776). We compute it directly because zxcvbn assumes a
  human chose the password and under-counts random ones (it said 53 bits for a 100-bit password — a bug we fixed).
- The EFF large wordlist (7,776 words) ships as `public/data/eff_wordlist.json`.

## 7. ML Lab

**What it does.** Explains the "second opinion" model shown on the Analyzer: accuracy, a confusion matrix, which
features matter most, and a table of passwords where the model and zxcvbn disagree.

**How we built it.**
1. **Data** — `ml/build.py` generates 60,000 *synthetic* passwords: weak ones from human habits (word + year,
   keyboard walks…), medium ones from mixed rules, strong ones from random characters or passphrases. No real
   passwords are used.
2. **Features** — 17 numbers per password (`ml/features.py`): length, character classes, entropy, repeats,
   sequences, keyboard runs, how word-like it is, dictionary coverage, trailing digits, year, leetspeak, capitalisation.
3. **Model** — scikit-learn **RandomForest** (40 trees). Held-out accuracy 99.8%.
4. **Export** — the trees are saved as JSON (0.37 MB) and evaluated in TypeScript (`lib/data.ts`), so the model runs
   in the browser with no ML library.
5. **Parity test** — the same features are written in Python and TypeScript; `frontend/scripts/parity.mts` checks 60
   sample passwords give identical numbers.

Honest caveat (also shown on the page): the labels come from how each password was generated, so 99.8% measures how
well the model learned those patterns — not real-world crack resistance.

## Backend API

FastAPI service with seven endpoints (`docs/API.md`): health, server-side hash timing, rainbow info and lookup,
audit, sample CSV, PDF. Rate-limited per IP with slowapi, CORS restricted to our site, no database.

## Deployment

Frontend on Firebase Hosting, backend on Render's free tier, code on GitHub with auto-deploy. Details and commands in
`docs/DEPLOYMENT.md`.
